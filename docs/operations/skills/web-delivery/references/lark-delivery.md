# Web Lead Lark delivery

For CoderPush Web milestones with a recorded originating Agentic Marketing user message, use `web-lead-notify ISSUE --reply-to SOURCE_MESSAGE_ID --milestone started|preview|blocked|recovered|shipped|decision --body-file FILE`. This writes an authorized structured outbox comment. This transport comment is the narrow exception to normal one-final-comment guidance; it is not a human-visible delivery receipt. The root-owned service replies as Web Lead in that original Lark thread. Read `multica issue metadata get ISSUE --key lark_delivery --output json` and match request_id before claiming delivery; state=sent includes the real message_id. Never say sent for queued, duplicate without a sent original, rejected, failed, or uncertain. An uncertain send requires operator reconciliation; do not requeue or reword to evade deduplication. Send only meaningful changed milestones, one concise message, no polling noise. Do not use raw credentials or direct Lark HTTP calls. Use recorded lark_origin metadata; do not invent a message ID. If chat history is unavailable in a scheduled/non-chat task, say so and use sourced issue/run evidence; do not imply reading the live conversation.
Separate stakeholder action from operator action. "No action for Anh" is compatible with "operator repair underway"; do not say "no action for Harley" when an infrastructure, access, or runtime blocker actually needs the operator. Report cause as verified or suspected, current owner, next action and next verification. Do not repeatedly retry known runtime failures or release without required evidence.

## Comment-triggered notification requests
The supported web-lead-notify helper accepts --parent <trigger-comment-id>. For a comment-triggered run, pass the Multica trigger comment ID to this flag; the Lark source message still belongs in --reply-to. Direct runs may omit --parent. Multica enforces the allowed parent. A queue failure is not delivery: reconcile actual comments (including replies) and the receipt before another attempt. Never claim delivery from an older request's receipt. Prefer one shipped update after current production verification; avoid repeating intermediate messages that are already superseded.
